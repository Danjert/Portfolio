# Executive Security Report: Corridor Web Application Analysis

## Executive Summary
A security assessment was performed on the **Corridor** web application environment to evaluate the integrity of resource identifiers, input validation mechanisms, and session authorization controls. The assessment uncovered critical design flaws, including predictable resource identification and the use of weak, reversible cryptographic hashing algorithms for endpoint protection. These vulnerabilities allow unauthenticated external actors to bypass logical access boundaries and access unauthorized resources.

---

## Scope & Framework Mapping
* **Assessment Objective:** Evaluate web application path security, parameter predictability, and access control enforcement.
* **Core Methodologies:** Endpoint enumeration, cryptographic primitive identification, hash reversal analysis, and boundary testing.
* **Standards & Framework Alignment:**
  * **NIST CSF 2.0:** Protect (PR.AA - Identity Management, Authentication, and Access Control; PR.DS - Data Security)
  * **NIST SP 800-53 Rev. 5:** AC-3 (Access Enforcement), SC-13 (Cryptographic Protection), SI-10 (Information Input Validation)
  * **MITRE ATT&CK:** T1595.002 (Active Scanning: Vulnerability Scanning), T1110.002 (Brute Force: Password Cracking / Hash Reversal)
  * **OWASP Top 10 (2025):** A01:2025 – Broken Access Control, A04:2025 – Cryptographic Failures

---

## Detailed Findings & Risk Analysis

### 1. Predictable Resource Identifiers & Weak Hashing (OWASP A02, NIST SC-13)
* **Vulnerability Description:** The web application relied on 32-character hexadecimal strings within URL paths to represent room identifiers. Forensic analysis established that these values were generated by applying an unsalted **MD5 hash** function to sequential integers (`1` through `13`).
* **Business & Operational Impact:** Using weak cryptographic hashes to conceal resource URLs introduces **security through obscurity** rather than genuine authorization. Because MD5 is computationally inexpensive to reverse via dictionary/brute-force techniques or generate for adjacent integers, external actors can easily enumerate the entire application namespace and access unauthorized restricted endpoints.

### 2. Absence of Server-Side Session Validation (OWASP A01, NIST AC-3)
* **Vulnerability Description:** The application evaluated HTTP requests based solely on whether a provided path string resolved to an active entry point, omitting proper session checks, user roles, or context-aware authorization validation.
* **Business & Operational Impact:** This absence of validation permitted unrestricted movement to unlinked nodes (such as root boundaries or administrative pathways), directly undermining the confidentiality and integrity of application resources.

## Detailed NIST Framework Mapping & Control Analysis

To ensure complete alignment with federal and enterprise governance standards, the findings identified during the Corridor assessment have been mapped to specific controls within **NIST SP 800-53 Rev. 5** and functions under the **NIST Cybersecurity Framework (CSF) 2.0**.

### 1. NIST SP 800-53 Rev. 5 Control Implementation Analysis

* **AC-3 (Access Enforcement):**
  * **Requirement:** The information system must enforce approved authorizations for logical access to information and system resources in accordance with applicable access control policies.
  * **Observation:** The application failed to enforce authorization checks on path parameters, allowing any actor who computed or guessed a valid MD5 hash to traverse application resources freely.
  * **Remediation Requirement:** Implement centralized, server-side session and role validation (RBAC) to ensure resource requests explicitly verify user privileges before rendering data.

* **SC-13 (Cryptographic Protection):**
  * **Requirement:** The organization must control the use of cryptography in accordance with federal standards and guidelines for cryptographic modules.
  * **Observation:** The application relied on an obsolete, collision-prone hashing algorithm (MD5) to conceal sequential resource identifiers in URLs.
  * **Remediation Requirement:** Discontinue the use of legacy cryptographic hashing primitives for data concealment. Enforce modern more robust cryptographic standards **(Recommended)** or transition resource references to unguessable, randomized identifiers (such as UUIDv4).

* **SI-10 (Information Input Validation):**
  * **Requirement:** The information system must check the validity of information inputs where errors or malformed structures could introduce vulnerabilities.
  * **Observation:** The application accepted unvalidated hexadecimal strings directly into routing logic without validating input integrity or contextual session state.
  * **Remediation Requirement:** Implement strict input sanitization, type validation, and boundary verification across all routing parameters.

### ### 2. NIST CSF 2.0 Function Alignment

* **Protect (PR) Function:**
  * **Identity Management, Authentication, and Access Control (PR.AA):** Access permissions and authorizations are managed, enforced, and audited in alignment with user and system roles. *Corridor finding highlights a direct failure in enforcing PR.AA controls across dynamic routing endpoints.*
  * **Data Security (PR.DS):** Data-at-rest, data-in-transit, and data-in-use are protected consistent with the organization's risk strategy to ensure confidentiality, integrity, and availability. *Corridor finding demonstrates how weak parameter protection, cryptographic obscurity, and missing authorization checks undermine data security posture, resulting in the unauthorized disclosure of protected application assets (the flag).*

* **A01:2025 – Broken Access Control:** 
  * *Context:* Remains the top risk category, explicitly encompassing authorization failures and improper enforcement of boundary restrictions. 
  * *Corridor Finding:* The application lacks server-side authorization checks on dynamic routing endpoints, allowing unauthenticated actors to traverse application limits and access protected resources (the flag) via IDOR.

  * *Context:* Covers the use of weak or outdated algorithms (such as MD5) to protect or obscure identifiers. 
  * *Corridor Finding:* The reliance on deterministic MD5 hashing to "hide" sequential door numbers introduced a false sense of security through obscurity, which was successfully reversed via offline computational utilities (`John the Ripper`, `Name That Hash`).

## Strategic Recommendations & Remediation Plan

1. **Implement Robust Access Controls (NIST AC-3):**
   * Enforce strict, server-side session validation and role-based authorization checks for all application routes. Do not rely on unauthenticated request parameters or path obfuscation to secure sensitive endpoints.
2. **Eliminate Predictable Identifiers:**
   * Replace sequential integer mappings and weak hashes with cryptographically secure, unpredictable resource identifiers (such as **UUIDv4**) when direct object references must be exposed to clients.
3. **Adopt Modern Cryptographic Standards (NIST SC-13):**
   * Discontinue the use of legacy, collision-prone hashing algorithms (such as MD5 and SHA-1) for any security-sensitive operations or resource mapping.
